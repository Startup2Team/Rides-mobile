SECTION 1 — ONBOARDING & AUTHENTICATION
1.1 Get Started Screen
The Get Started screen must be minimal. Collect only what is strictly needed to create an account — no friction, no unnecessary fields.

Keyboard type: Use numeric keyboard (keyboardType='phone-pad') so the number pad appears immediately with no layout shift.
OTP length: After submitting the phone number, send a One-Time Password. Prompt the user with a top-code input of exactly 4 or 6 digits (configurable). Use a segmented OTP input component — one box per digit — so the keyboard never obscures the flow.
Auto-submit: When the last digit is entered, auto-submit the OTP without requiring a confirm button.
Resend timer: Show a resend countdown (60 seconds). After it expires, show a Resend Code button.

1.2 Permissions & Initial Load
Immediately after successful OTP verification:
1.Request Location permission (expo-location or react-native-permissions). Show a clear rationale dialog before the system prompt: 'We need your location to find nearby vehicles.'
2.Request Push Notification permission. Rationale: 'Enable notifications to get ride updates and driver messages.'
3.Once location is granted, resolve the user's exact GPS coordinates (high-accuracy mode).
4.Use those coordinates to fetch the nearest available vehicles from the backend.
5.The home screen must render centred on the user's exact current location — not a default city centre or generic pin. Do not show the map until GPS coordinates are resolved. Show a loading indicator while resolving.

SECTION 2 — CUSTOMER RIDE REQUEST FLOW
2.1 Location Input & Classification
When the customer enters or selects a pickup or destination address, the system must classify it into one of two categories:
•Precise location — a resolved GPS coordinate with a clear street address (e.g. from Google Places Autocomplete or map pin drop).
•Generic / Unknown location — a vague place name, a neighbourhood, a landmark without a specific address, or any input that cannot be resolved to a precise coordinate.

Handling Precise Locations: Proceed normally to ride request. Display ETA and fare estimate.
Handling Generic / Unknown Locations: Do NOT block the ride request. Send the request to the rider with the generic location label. The exact destination will be negotiated via the in-app chat. See Section 2.3 for the chat negotiation flow.

2.2 Ride Request Card (Customer View — Pre-Accept)
After submitting a ride request, the customer sees a waiting screen. This screen must show:
•A map centred on the customer's current location with nearby available riders shown as vehicle icons.
•A ride summary card with: pickup label, destination label (or 'To be confirmed' for unknown locations), and estimated distance if known.
IMPORTANT: The ETA card and destination summary card must be visually distinct from the pickup/drop-off detail form below them. Do not mix card components with form input components. Cards are read-only display elements; forms are input elements. They must not share the same container or styling.

2.3 Negotiation Chat — Customer Side
When a rider accepts the request, a negotiation chat opens between the customer and rider.

First Message Rule
If the location is Generic or Unknown, the system must automatically send the location details as the very first message in the conversation on the customer's behalf — before the customer types anything. This message is system-generated and reads: 'My destination is [location label]. Please let me know your price.'
The customer does NOT initiate the price. The rider makes the first price offer. The customer only responds with a counter-offer.

Chat Rules
Remove suggested price: Do not show a system-suggested or algorithm-generated price in the chat. No price hints, no fare estimates shown in the negotiation window.
Message counter: Display a live message counter (e.g. '2 / 3 messages used'). The maximum number of text messages in the negotiation is 3 per side.
Call button trigger: Once the message limit of 3 is reached OR at any point after the rider sends their first offer, show a persistent Call button alongside the action buttons.

Action Buttons — Customer Negotiation Screen
At all times during negotiation, show exactly three action buttons:
•Accept — customer accepts the rider's current offer.
•Decline — customer declines and cancels the negotiation.
•Call — initiates a phone call to the rider via the device dialler.
These three buttons must always be visible once negotiation begins. Do not hide or disable the Call button at any stage.

2.4 Post-Acceptance — Customer Waiting View
Once the customer taps Accept and the rider confirms the agreed amount:
6.Show a confirmation screen with: agreed fare, rider name, vehicle type, plate number.
7.Display a live map showing the rider's real-time location moving toward the pickup point.
8.Show ETA of rider arrival at pickup, updating in real time.
9.When the rider taps 'I Have Arrived' on their side, the customer receives a push notification AND the in-app screen updates to show: 'Your rider has arrived. Please come to the pickup point.'

2.5 Active Journey — Customer View
Once the rider taps Start Journey:
•Show a live map with the route from pickup to destination, rendered using Google Maps Directions API.
•Show ETA to destination, updating in real time.
•Show an End Journey button. This button is for emergency/early termination only — normal ride completion is handled on arrival.
•On arrival at the destination, show a Complete Ride button. The customer taps this to confirm the ride is finished 

SECTION 3 — RIDER (DRIVER) FLOW
3.1 Incoming Ride Request — Rider Side
When a new ride request comes in, the rider sees a notification and a request card showing:
•Customer name 
•Pickup location label.
•Destination label (or 'Unknown — to be negotiated' if generic).
•Route direction  to pickup.

The rider taps Accept to open the negotiation chat. They do NOT see a suggested price. They must generate their own offer based on the location.

3.2 Negotiation Chat — Rider Side
After accepting the request, the rider sees the negotiation chat with:
•Customer info card at the top: name, pickup address, destination (or generic label).
•If the location is Generic or Unknown, the customer's system-generated first message is already visible.

Rider Action Flow
10.Rider types and sends their price offer as the first message (e.g. '3000 RWF').
11.Customer replies with a counter-offer or accepts.
12.Maximum 3 messages per side. After limit, Call button becomes prominent.

Action Buttons — Rider Negotiation Screen
•Accept — rider accepts the customer's counter-offer.
•Decline — rider declines and the request is released back to the pool.
•Call — calls the customer.

Agreed amount entry: When the rider taps Accept, a small modal or inline input appears asking: 'Enter the final agreed amount (RWF).' The rider types the amount. This amount is stored, shown to both parties

3.3 Navigation to Pickup — Rider Side
After the agreed amount is confirmed:
13.Show a live map with directions from the rider's current location to the customer's pickup point (Google Maps Directions API).
14.Show ETA to pickup, updating in real time.
15.When the rider arrives at the pickup location (geofence trigger or manual confirmation), show an 'I Have Arrived' button.
16.Tapping 'I Have Arrived' sends a push notification to the customer and starts a waiting timer.

3.4 Waiting Timer & Cancellation
After the rider taps 'I Have Arrived':
•A countdown timer starts: 3 minutes (configurable in app settings, default 3 minutes).
•The timer is visible to the both side rider and customer on screen.
•During this window, the rider sees two options: Wait (default) and Cancel Ride.
•If the timer expires without the customer boarding, the Cancel Ride button becomes highlighted with a prompt: 'Customer has not arrived. You may cancel this ride.'
•Cancellation releases the rider back into the available pool. A cancellation reason is logged.
•A Call button is also present throughout so the rider can reach the customer.

3.5 Active Journey — Rider Side
When the customer arrives and boards the vehicle, the rider taps Start Journey:
•Map switches to show the route from pickup to destination with turn-by-turn navigation (Google Maps).
•Google Maps route suggestions and shortcut alerts must be enabled. If a faster route is found, show a banner: 'Faster route available' with a Reroute button.
•Show an End Journey button for emergencies.
•On arrival at destination, show Complete Ride button. Rider taps it to end the trip

17.Clear all local session tokens and user state.
18.Navigate the user to the Get Started screen.
19.Stop all background location updates and socket connections.

4.2 Become a Rider (Customer to Rider Upgrade)
Any existing customer can apply to become a rider. The 'Join as Rider' button must:
•Pre-fill the rider registration form with the user's phone number and name  pulled from their existing customer profile. The user should not have to re-enter information they already provided.
•The rider registration then continues with the vehicle and document steps below.

SECTION 5 — RIDER REGISTRATION FORM
5.1 Location Hierarchy — Rwanda
All location fields in the rider registration form must use a cascading dropdown hierarchy specific to Rwanda's administrative structure. Each level loads dynamically based on the selection above it:
20.Province (5 provinces: Kigali City, Northern, Southern, Eastern, Western)
21.District (30 districts total, filtered by selected province)
22.Sector (filtered by selected district)
23.Cell (filtered by selected sector)
24.Village (filtered by selected cell)
All location data must be sourced from Rwanda's official administrative boundary data. Do not allow free-text entry for these fields.

5.2 Vehicle Information Form
The rider selects their vehicle type from the available options. Do NOT include any amount, pricing, or fare fields on the vehicle information form — these are negotiated per ride.

Vehicle Type — Conditional Follow-up Questions
When a rider selects a vehicle type, the form dynamically shows follow-up questions specific to that type. Examples:
•Cab / Taxi: 'How many passenger seats does your vehicle have?' (number input, min 1)
•Motorcycle (Moto)
•Hilux
•Truck: 'What is the maximum load capacity in kg?' (number input)
Every vehicle type must define its own set of follow-up questions. Do not show irrelevant fields.

5.3 Plate Number Validation — Rwanda Formats
All plate number inputs must be uppercase only (force toUpperCase on input). Rwanda uses the following formats — validate against these:
•Private vehicles: RAA 000 A (3 letters + space + 3 digits + space + 1 letter)
•Commercial vehicles: RAC 000 A (same pattern, starts with RAC)
•Motorcycles: RAD 000 A or similar motorcycle-prefixed codes
Show a real-time format guide below the input field as the user types. If the format does not match any known Rwanda pattern, show a validation warning (not a hard block — the fleet may include special cases).

5.4 Document Uploads
The rider must upload the following documents. Each upload field accepts JPEG, PDF or PNG. Show a preview thumbnail after upload. Mark each as Required:
•Driver's Licence photo (front face)
•Vehicle Insurance document photo
•Vehicle Authorization / Inspection certificate photo

5.5 Payment Setup
The rider sets up how they will receive payments. Options:
•Mobile Money phone number (MTN MoMo or Airtel Money)
•MoMo code (merchant code if applicable)
Only one payment method is required. The rider picks one via a toggle or radio selector. Do not require both.

5.6 Terms & Policies Agreement
At the bottom of the registration form, show a single checkbox with the label: 'I agree to the Terms of Service and Privacy Policy.' This is one checkbox covering both documents (link each separately in the label text). Do NOT split into multiple checkboxes per policy. The registration submit button is disabled until this checkbox is checked.

SECTION 6 — MAP & REAL-TIME REQUIREMENTS
6.1 Map Provider
Use Google Maps (react-native-maps with Google Maps provider on Android; Apple Maps or Google Maps on iOS). All route calculations must use the Google Maps Directions API.

6.2 Route Display Rules
•Always show the fastest route by default.
•Turn-by-turn directions must be shown for the rider during active journey.
•For the customer, show the route as a polyline overlay on the map — AND also turn-by-turn is needed on customer side.

6.3 Real-Time Location Sync
•Rider location must update every 3–5 seconds during an active ride.
•The customer's map must reflect the rider's updated location smoothly (animate marker movement).
•ETA values must recalculate on each location update.

SECTION 7 — STATE MACHINE & EDGE CASES
7.1 Ride State Definitions
The system must enforce exactly one ride state at a time per active booking. States and valid transitions:
PENDING: Customer submitted request, waiting for rider to accept.
NEGOTIATING: Rider accepted; chat is open; price not yet agreed.
ACCEPTED: Price agreed; rider navigating to pickup.
ARRIVED: Rider has tapped 'I Have Arrived'; waiting timer active.
IN_PROGRESS: Journey started; rider navigating to destination.
COMPLETED: Both parties confirmed arrival; ride closed.
CANCELLED: Cancelled by either party at any valid stage.

7.2 Loophole Closures
The following rules prevent exploits and broken states:
•A rider cannot accept a second ride while in ACCEPTED, ARRIVED, or IN_PROGRESS state.
•A customer cannot submit a new ride request while in NEGOTIATING, ACCEPTED, ARRIVED, or IN_PROGRESS state.
•The Complete Ride button is only shown when the device is within 200 metres of the destination coordinate.
•The Start Journey button is only shown when the rider is in ARRIVED state — not before.
•If a rider cancels during the ARRIVED waiting window, the customer receives a notification: 'Your rider cancelled. Searching for a new rider.'
•If the negotiation message limit (3 messages) is reached with no agreement, the system does not auto-cancel. The Call button is shown prominently. Either party can Decline to cancel.
•The agreed fare entered by the rider on Accept cannot be zero or negative. Validate before submission.
•OTP codes expire after 5 minutes. Expired codes must be rejected and a new one requested.

SECTION 8 — UI / UX CONSTRAINTS
8.1 Keyboard Behaviour
No screen should allow the keyboard to cover primary action buttons. Use KeyboardAvoidingView with appropriate behaviour ('padding' on iOS, 'height' on Android) on all screens with text inputs.

8.2 Loading States
Every async operation (GPS resolve, API fetch, OTP send, route calculation) must show a loading indicator. The map must not render with a default/fallback location — wait for actual GPS resolution.

8.3 Button States
All action buttons must have three visual states: Default, Loading (spinner), and Disabled (greyed out). Never allow double-tapping to submit a request twice — disable the button immediately on first tap.

8.4 Cards vs Forms
ETA cards, destination summary cards, and ride info cards are display-only components. They must be visually distinct from input forms. Cards use a rounded elevated surface. Forms use standard input fields with labels. Do not render them in the same parent container or with matching styles.
